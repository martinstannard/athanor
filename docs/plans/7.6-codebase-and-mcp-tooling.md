## 1. Scope & Non-goals

### In scope
- Two new built-in workspace tools — **`glob`** and **`grep`** — implemented in pure Elixir (no shell),
  shared by Conductors and Sub-Agents, alongside the existing four (`read_file`, `write_file`,
  `edit_file`, `bash`).
- A **Tool Guard** with **prelude-read enforcement**: per-session tracking of files successfully
  read, and a refusal path for `edit_file`/`write_file` against *existing* files that were never
  read in that session.
- An **MCP client (`Athanor.MCP`)** speaking JSON-RPC 2.0 over **stdio** and **SSE**, attaching MCP
  servers per Conductor / Sub-Agent *profile*, discovering their tools, namespacing them into the
  OpenAI tool schema, and dispatching `tools/call`.
- New config accessors, new supervision children, new security controls (command allowlists, opt-in
  project config), unit + integration tests, and a phased rollout that always ends green.

### Non-goals (explicitly excluded)
- **Not** implementing §7.1 worktrees — but `glob`/`grep`/MCP all resolve paths against the session
  `cd` via `Tools.resolve_path/2`, so a future worktree `cd` is honoured for free.
- **Not** implementing §7.2 goals/verifiers or §7.3 watchers. MCP tools are *just tools*: no goal
  semantics, no verification.
- **Not** implementing §7.4 persistence — the guard read-set and MCP tool caches stay **in memory**.
  Neither survives a VM restart.
- **Not** a general code-intelligence layer: no LSP, no tree-sitter, no symbol index. `glob`/`grep`
  are bounded text search, nothing more.
- **Not** making MCP *resources*, *prompts*, *sampling*, or *roots* first-class. Only the `tools/*`
  surface is consumed in v1; server→client requests get a `-32601` reply (see §5.3).
- **Not** exposing MCP tools to the TUI or Daemon RPC directly (only through `Tools.schemas/1`).
- **Not** adding a dependency for MCP (hand-rolled over `Port` + `Req`); see §11 OQ-M3.

Ordering rationale (mirrors the existing tree): registries and the ETS owner start **before** any
child that registers into them. `ToolGuard` and `MCP.Registry` precede `AgentSupervisor` and
`MCP.Supervisor` respectively. Restart policy for `MCP.Server` is `:transient` (unlike
`Athanor.Agent`'s `:temporary`): a *clean* stop is intentional detach, but an abnormal exit should be
retried by the supervisor, with the reconnect re-running the handshake and republishing tools.

### 2.4 Where per-session state lives (the Tool Guard problem)

Two per-session stores are introduced, and they have *different* homes:

1. **MCP attachment** (`mcp_profile :: String.t() | nil`, `mcp_tools :: [map()]`): belongs in the
   **`Athanor.Agent` struct** (`lib/athanor/agent.ex:38`). It is written once at `init/1`, read by
   the Agent itself in `start_llm_turn/1`, and never touched by the tool runner. Pure struct state.

2. **Read-set (prelude-read enforcement)**: cannot live *only* in the Agent struct, because writes to
   it happen inside the **spawned tool-execution process** (**G3**), which has no access to the
   GenServer's state. The recommendation, in order of preference:

   - **Recommended [PROPOSED]:** a dedicated ETS-backed owner, **`Athanor.ToolGuard`**, started in
     `Athanor.Application`, owning a `:public` table `:athanor_tool_guard` with
     `read_concurrency: true, write_concurrency: true`, keyed by `{session_id, abs_path}`. The Agent
     calls `ToolGuard.reset(state.id)` in `init/1`; `Athanor.Tools.execute/3` calls
     `ToolGuard.read?(opts[:session_id], abs_path)` and `ToolGuard.mark_read/2` — using the
     `:session_id`/`:cd` opts already present (**G2**). The Agent struct then *optionally* mirrors a
     snapshot into a new `read_paths` field purely for observability via `get_state` — it is **not**
     the source of truth.
   - **Alternative (rejected):** thread the read-set through `opts` as
     `opts[:read_paths]` and re-sync via a `{:read_paths_updated, set}` message emitted at the end of
     `start_tool_execution/2`. Rejected because a batch of tool calls executes sequentially in one
     process (**G3**) and the sync is post-hoc: a `read_file` in the *same* batch could not satisfy a
     guard in the *next* batch until the message is processed, and the round-trip is easy to lose on
     `:cancel`/`kill_current_task/1`.
   - **Rejected outright:** storing the read-set inside `Athanor.Agent` only. It is unreachable from
     the tool process and would silently no-op.

> Cleanup: guard entries are removed by `ToolGuard.reset/1` on `Agent.terminate/2`
> (and defensively at `init/1`, to make test restarts deterministic).

## 3. Built-in `glob` and `grep` tools

### 3.1 Behaviour, and how they differ from `bash`

| | `glob` / `grep` | `bash` (`"ls"`, `"find"`, `"rg"`, `"grep"`) |
|---|---|---|
| Output shape | Bounded, **structured** strings (`path` or `path:line:content`), always truncated | Raw combined stdout/stderr, unbounded up to the 30 s wall clock |
| Failure mode | `{:error, "…"}` describing the *search* problem | `{:error, "Command exited with status N:\n…"}` — the model must parse shell noise |
| Injection surface | None: pattern is a *pattern*, never a command string | Full shell (`System.cmd("bash", ["-c", command])` in `execute("bash", …)`) |
| Environment dependence | Deterministic: `rg`/`grep` may be absent, versions differ, aliases differ | Depends entirely on the host's installed tools |
| Cost control | Hard caps (`max_results`, `max_file_bytes`) enforced **before** stringification | The model invents its own pipes; nothing stops `find / -type f` |
| Ignore discipline | Enforces the project's ignore rules centrally, every call | The model must remember `--exclude-dir`/`.gitignore` flags each time |

The point of shipping these built-ins is **not** novelty — it is removing a whole class of model
failure modes: shell-quoting errors, unbounded output blowing the context window, missing binaries,
and non-reproducible results. `bash` remains available for genuinely arbitrary work; it is no longer
the *only* way to answer "which files match this?" or "where is this symbol used?".

### 3.2 `glob` semantics
- Pattern syntax: `*`, `?`, `**`, `{a,b}` — the subset `Path.wildcard/2` supports.
- Root: `path` param (optional) or `Path.expand(opts[:cd])` via `Tools.resolve_path/2` (**G5**).
- Implementation **[PROPOSED]**: enumerate with `Path.wildcard(Path.join(root, pattern), match_dot: false)`,
  then filter through `Athanor.Tools.Ignore`, keep only regular files, sort, and cap at
  `max_results` (default `Config.search_max_results/0`, 200).
- Returns **paths relative to `path`** (not absolute), one per line, so the model can feed them
  straight back into `read_file`.
- A truncation notice is appended when the cap is hit:
  `"… (truncated: 200 of 1,412 matches; narrow the pattern or raise max_results)"`.
- Empty result: `{:ok, "(no files matched)"}` — never `{:ok, ""}`, which reads as a transport bug.

### 3.3 `grep` semantics
- `pattern` is compiled with `Regex.compile/2` (Elixir's `:re` → **PCRE**). `case_sensitive`
  (default `true`) toggles the `"i"` option. An invalid pattern is a **user error**, not a crash:
  `{:error, "Invalid regular expression: <reason>"}`.
- `path` may be a directory (walk) or a single file. `glob` optionally restricts the file set
  (reusing `Athanor.Tools.Glob`); `ignore` adds project-specific exclusions.
- Reads files with `File.stream!/3` line-by-line; for each line, `Regex.run/2`; emits
  `"#{rel_path}:#{line_no}:#{line}"`.
- **Binary/heavy-file protection** (§3.4) applies before any regex work.
- Same `max_results` cap and truncation notice as `glob`.

### 3.4 Ignore rules (shared by `glob` and `grep`) — `Athanor.Tools.Ignore` **[PROPOSED]**

Three layers, applied in this order:

1. **Hard-coded safety denies** (never overridable from the model side):
   `.git/`, `_build/`, `deps/`, `node_modules/`, `cover/`, `.elixir_ls/`, `.athanor/`, plus
   `*.beam`, and any path containing a NUL in its name.
2. **`.gitignore`** at the search root (and nested). Parsing is a deliberately small subset:
   comments (`#`), negations (`!`), directory-only (`trailing /`), `*`/`**`/`?` globs.
   **[OPEN]** whether to vendor a matcher or take a dependency (§11 OQ-S1).
3. **Caller-supplied `ignore` patterns** from the tool arguments (`opts[:cd]`-relative).

Additional file-level guards, independent of ignore rules:
- **Skip symlinks by default** (prevents cycles and escaping the root via a symlinked parent).
- **Skip files larger than `Config.search_max_file_bytes/0`** (default 1 MiB).
- **Skip binary files**: read the first 8 KiB, reject if a `NUL` byte is present.

> **Why the guardrails matter for the LLM:** an agent that can emit unbounded output can destroy its
> own context window in one call, and an agent that can escape the working directory can read
> `~/.ssh` and `~/.local/share/opencode/auth.json` (the credential store `Config.read_opencode_auth_key/1`
> reads). Bounded, rooted, ignore-aware search is a *context-budget* control and a *blast-radius*
> control at the same time — not a convenience.

## 4. Tool Guard & Prelude-Read Enforcement

### 4.1 The problem (C6)
`execute("write_file", …)` **overwrites unconditionally** and `execute("edit_file", …)` only fails if
`old_string` is missing or ambiguous. Neither reads the file first. A model that guesses a path can
therefore replace an existing file's entire contents with a hallucination, and nothing in the current
code records that the file was ever *seen*. `read_file`'s result is the only source of truth, and it
is optional today.

### 4.2 Rule
> **A session may only `edit_file`/`write_file` a path that already exists on disk if it has
> successfully `read_file`-ed that same resolved path earlier in the session.**

Precise semantics (all required, all testable):

| Case | Result |
|---|---|
| `write_file` to a **non-existent** path | **Allowed** (creation, incl. `File.mkdir_p/1`) |
| `write_file` to an **existing** path, never read this session | **`{:error, "Refusing to overwrite <path>: it exists and has not been read in this session. Call read_file first."}`** |
| `write_file` to an **existing** path, previously read | Allowed |
| `edit_file` on an existing path, never read | Same refusal error |
| `edit_file` on a path, previously read | Allowed (existing not-found / multi-match errors unchanged) |
| `read_file` success | Records the **resolved absolute path** in the read-set |
| `write_file`/`edit_file` success | Also records the path (post-write content is now known) |
| Guard disabled (`Config.tool_guard_enabled?/0 == false`) | Everything allowed (escape hatch for tests/advanced users) |

Path **canonicalisation is mandatory**: the read-set is keyed on `Path.expand(path, cd)`
(i.e. `Tools.resolve_path/2`) so `./lib/x.ex`, `lib/x.ex`, and `lib/../lib/x.ex` are one entry.
Symlinks are **not** resolved (deliberate: the model's mental model is path strings).

### 4.3 Structure: where the checks go

```text
Athanor.Agent.start_tool_execution/2   (agent.ex:397)
  └─ spawn_monitor(fn -> Enum.map(tool_calls, fn tc ->
         Tools.execute(name, raw_args, cd: cd, session_id: session_id)   # session_id = state.id (G2)
       end) end)

Athanor.Tools.execute("read_file", %{"path" => p}, opts)
  │  before  -> (nothing)
  │  on {:ok, _} -> Athanor.ToolGuard.mark_read(opts[:session_id], resolve_path(p, opts))
  └─ returns {:ok, content}

Athanor.Tools.execute("write_file" | "edit_file", %{"path" => p}, opts)
  │  abs = resolve_path(p, opts)
  │  if File.exists?(abs) and guard_enabled? and not ToolGuard.read?(opts[:session_id], abs)
  │     -> {:error, "Refusing to overwrite …"}          # never spawns a write
  └─ otherwise existing behaviour, then ToolGuard.mark_read/2 after success
```

`Athanor.ToolGuard` **[PROPOSED]**:

```elixir
defmodule Athanor.ToolGuard do
  @moduledoc """
  Per-session prelude-read enforcement (design §7.6). Backs the "read before write"
  invariant with an ETS read-set keyed by {session_id, absolute_path}.
  """
  @table :athanor_tool_guard

  @spec start_link(keyword()) :: GenServer.on_start()
  @spec mark_read(String.t(), String.t()) :: :ok
  @spec read?(String.t(), String.t()) :: boolean()
  @spec snapshot(String.t()) :: MapSet.t(String.t())
  @spec reset(String.t()) :: :ok
end
```

- Table options: `[:set, :public, read_concurrency: true, write_concurrency: true]`. Public (not
  protected) because writes originate in the spawned tool process, which is not the table owner.
- `reset/1` uses `:ets.match_delete(@table, {{session_id, :_}, :_})`.
- Guard is a **no-op** when `Athanor.PubSub`/`AgentRegistry` are absent — it must never be a reason
  `Tools.execute/3` fails in a bare unit test (mirrors `Bus.subscribe/1`'s `Process.whereis` guard).
- **[OPEN]** Should a *rejected* write also be reported as a PubSub event (`{:tool_end, {:error, _}}`
  already carries it to the TUI via `start_tool_execution/2`, so a *new* event is likely unnecessary).
  Recommendation: no — the existing `{:tool_end, name, {:error, err}}` path is sufficient.

### 4.4 Why not just rely on the prompt?
Because a prompt instruction is advisory and unverifiable, and the failure is *destroying user data*.
Enforcement belongs in the executor where it is total and testable. The refusal message is
deliberately actionable ("Call read_file first") so the model self-corrects in one turn rather than
retrying the same call.

| Transport | Mechanism | Notes |
|---|---|---|
| **stdio** | `Port.open({:spawn_executable, exe}, [:binary, :exit_status, args: args, cd: cd, env: env, {:line, 1_048_576}])` | Newline-delimited JSON-RPC 2.0 (MCP stdio framing: one object per line, no embedded newlines). `Port` messages `{port, {:data, {:eol, line}}}` / `{port, {:exit_status, n}}` are delivered to the owning `MCP.Server`. **Never** `bash -c`. |
| **SSE** | `Req` GET on the SSE endpoint; server emits an `endpoint` event carrying a POST URL; client POSTs JSON-RPC there and reads responses from the event stream | Uses the existing `req` dep (**no new dependency**). Requires a dedicated reader process; TLS-only (`https://`). |

`Athanor.MCP.Transport` **[PROPOSED]** behaviour:
```elixir
@callback open(config :: map(), owner :: pid()) :: {:ok, ref :: term()} | {:error, term()}
@callback send(ref :: term(), payload :: map()) :: :ok | {:error, term()}
@callback close(ref :: term()) :: :ok
# owner receives: {:mcp_message, ref, decoded_map} | {:mcp_exit, ref, reason}
```

### 5.2 Handshake
1. `initialize` request → `{protocolVersion, capabilities: %{}, clientInfo: %{name: "athanor", version: "0.1.0"}}`.
2. Await the response (`Config.mcp_handshake_timeout_ms/0`, default 10 s) → record `serverInfo` +
   `capabilities.tools`.
3. Send `notifications/initialized` (a notification — **no `id`**, no response expected).
4. `tools/list` (paginated by `cursor`) → cache `[%Athanor.MCP.Tool{}]`.
5. `ping` on a heartbeat is **optional**; liveness comes from `{:mcp_exit, …}`.
6. A server that fails the handshake is marked `:error`, is **not** retried in v1, and contributes
   **no tools** — a broken server must never wedge `Tools.schemas/1`.

### 5.3 Server → client requests
MCP servers may issue requests (`roots/list`, `sampling/createMessage`). v1 replies
`{"jsonrpc":"2.0","id":id,"error":{"code":-32601,"message":"method not supported by Athanor"}}` to
everything except `roots/list`, which returns the session `cd` as a single root (cheap, useful, and
strictly read-only). **[OPEN]** whether to support sampling later (§11 OQ-M5).

### 5.4 Discovery & namespacing (**C4**)
- Each discovered tool maps to an OpenAI function tool with
  `"name" => "mcp__#{sanitise(server)}__#{sanitise(tool)}"`, where `sanitise/1` replaces any
  character outside `[A-Za-z0-9_]` with `_` and truncates so the whole name stays ≤ **64 chars**.
- Descriptions are prefixed `"[#{server}] "` and truncated to 1024 chars.
- **Schema normalisation** (**C5**): MCP `inputSchema` is JSON Schema; flatten `$ref`/`$defs` where
  possible, drop `oneOf`/`anyOf`/`not`/`if` in favour of `{}` (permissive), and target
  `"type" => "object"` with a `properties`/`required` pair. A schema that cannot be normalised
  degrades to `%{"type" => "object", "properties" => %{}}` — the tool stays callable.
- The reverse map `%{exposed_name => {server_key, original_name}}` is returned by `MCP.tools_for/1`
  and cached per server; `Tools.execute(<<"mcp__", _::binary>>, args, opts)` splits the name back.

### 5.5 Lifecycle
- **Attach:** `Orchestrator.start_conductor(mcp: "default")` / `launch_subagent(…, mcp: "data")` puts
  `:mcp` into the Agent opts; `Agent.init/1` calls `Athanor.MCP.attach(profile, self())` (async — it
  returns immediately with whatever is already discovered and the Agent re-reads tools each turn).
- **Reference counting:** a server is started once under `Athanor.MCP.Supervisor` and ref-counted by
  attached sessions; the last `detach/2` stops it cleanly (`:transient` restart does not fire on a
  clean stop). Sessions in the same `cd` with the same profile share the server (and share the
  process — a good reason for §9's blast-radius discussion).
- **Death:** `{:mcp_exit, ref, reason}` → `MCP.Server` marks itself `:down`, clears its tool list, and
  logs; subsequent `tools/call` for it returns
  `{:error, "MCP server '<key>' is unavailable (<reason>)"}`. The supervisor restarts it; the
  restarted server re-handshakes and republishes tools.
- **Detach:** `Agent.terminate/2` calls `Athanor.MCP.detach/2`; `MCP.Server.terminate/2` closes the
  port (`Port.close/1`) so stdio children do not leak. **[OPEN]** whether the daemon should keep
  servers alive across TUI detach — it should *not* (servers belong to sessions, not to clients).

### 5.6 Timeouts & errors
| Condition | Result handed to the model |
|---|---|
| `tools/call` response `isError: true` | `{:error, "MCP <server> tool <name> failed: <first text content>"}` |
| JSON-RPC `error` object | `{:error, "MCP <server> error <code>: <message>"}` |
| No response within `Config.mcp_request_timeout_ms/0` (30 s) | `{:error, "MCP <server> timed out after 30000ms"}`; a `notifications/cancelled` is sent |
| Server down / never attached | `{:error, "MCP server '<key>' is unavailable"}` |
| Output larger than `Config.mcp_max_output_bytes/0` (256 KiB) | Truncated with a notice |

Long calls **must not block the Agent**: `MCP.call_tool/4` is invoked from the spawned tool process
(`start_tool_execution/2`), which is already off the GenServer loop — the existing non-blocking
contract (`AGENTS.md`: "Never block the TUI process on HTTP requests or tool execution") is preserved
without change.

### 5.7 Attaching per profile
Profiles are named bundles of servers + a tool allow/deny list:

```json
{
  "mcpServers": {
    "linear": {
      "transport": "stdio",
      "command": "npx",
      "args": ["-y", "mcp-remote-linear"],
      "env": {"LINEAR_API_KEY": "${LINEAR_API_KEY}"},
      "timeout_ms": 30000
    },
    "postgres": {
      "transport": "stdio",
      "command": "mcp-server-postgres",
      "args": ["postgresql://localhost/app"]
    },
    "exa": {
      "transport": "sse",
      "url": "https://mcp.exa.ai/sse",
      "headers": {"Authorization": "Bearer ${EXA_API_KEY}"}
    }
  },
  "profiles": {
    "default": {"servers": ["linear", "exa"], "allow": ["linear.create_issue", "exa.*"]},
    "data":    {"servers": ["postgres"],      "allow": ["postgres.query"]}
  }
}
```

- `${VAR}` interpolation reads from the **process environment only** — never from the config file —
  so secrets do not have to be written to disk. Unset variables resolve to the empty string and the
  server is marked `:error` with a clear log line.
- `allow`/`deny` are glob patterns matched against `<server>.<tool>`; **`deny` wins**, and a profile
  with neither key exposes nothing (deny-by-default, not allow-by-default).
- Attach points: `Orchestrator.start_conductor(mcp: "default")`,
  `Orchestrator.launch_subagent(parent, title, prompt, mcp: "data")`. `Agent` stores
  `mcp_profile`; per-call, `Agent.start_llm_turn/1` calls
  `Tools.schemas(role: state.role, mcp_tools: Athanor.MCP.tools_for(state.mcp_profile))` (**G4**).

## 8. Security & Permission Considerations

### 8.1 MCP stdio = arbitrary local process execution
This is the headline risk of §7.6: a `"command"` in an MCP config is a **local binary executed with
the user's privileges**, in the user's filesystem, for the lifetime of the session. Controls, all
mandatory:

1. **Opt-in, never ambient.** A repository-local `.athanor/mcp.json` is **ignored** unless
   `mcp_allow_project_servers?/0` is explicitly true (env `ATHANOR_MCP_ALLOW_PROJECT=1`). Cloning and
   opening a repo must never spawn anything. (**C3**)
2. **No shell.** `Port.open({:spawn_executable, exe}, …)` with an `args` list — never
   `System.cmd("bash", ["-c", …])`. Config-provided `command` strings containing shell metacharacters
   (`;`, `|`, `&`, `$`, backticks, newlines) are rejected at load time.
3. **Executable allowlist.** `Config.mcp_command_allowlist/0` (default: `npx`, `uvx`, `node`, `python3`,
   `docker`, plus any absolute path the user adds). Anything else → the server is loaded as `:error`
   and never spawned. **[OPEN]** whether the default should be `:any` for developer convenience
   (§11 OQ-M2).
4. **Executable resolution.** `System.find_executable/1` on the bare command; reject empty results
   rather than letting the OS decide.
5. **Environment scrubbing.** Do **not** inherit `System.get_env/0`. Pass a minimal env
   (`PATH`, `HOME`, `LANG`, plus the server's declared `env` map). This prevents silently handing
   `OPENCODE_API_KEY`, `LINEAR_API_KEY`, AWS/GCP credentials, etc. to every MCP server.
6. **Working directory pinned** to the session `cd`, never the caller's cwd; `cd` itself is not
   model-controllable.
7. **Process hygiene.** Output capped (`mcp_max_output_bytes/0`); every request timed out; port
   closed in `MCP.Server.terminate/2`; no `:stdin` inheritance beyond the port.
8. **Audit.** Every spawn logs `key`, resolved executable, args (env values **redacted**), and `cd`.
9. **Per-profile least privilege.** `allow`/`deny` globs mean a Postgres server is never exposed to a
   web-research worker; deny-by-default when a profile omits both.

### 8.2 Untrusted MCP output (prompt injection)
MCP tool results are attacker-influenced text (a Linear issue body, a scraped page). Mitigations:
prefix results with the tool identity (`"[mcp:linear.create_issue] …"`), keep them in the `tool` role
(never `system`), and note in the MCP module `@moduledoc` that MCP content is untrusted data. File
writes performed *by* an MCP server are **outside** the Tool Guard's reach — a documented limitation
(§11 risk 6).

### 8.3 SSE
`https://` only (reject plaintext); `Authorization` headers sourced from env interpolations only;
header values redacted in logs and in `MCP.servers/1` snapshots; response bodies capped like stdio.

### 8.4 Tool Guard's own limits
The guard is a *footgun reducer*, not a sandbox: it stops blind overwrites by the current session, but
`bash` can still `rm -rf`, and each session has an independent read-set (a sub-agent reading a file
does not authorise its parent). Both are deliberate and documented.

## 10. Risks, Edge Cases & Open Questions

### Risks / edge cases
1. **`Path.wildcard/2` is not `.gitignore`-aware** (and treats `**` differently from ripgrep in a few
   corner cases). The custom `Athanor.Tools.Ignore` layer is therefore load-bearing, and its glob
   semantics must be tested explicitly rather than assumed.
2. **Symlink escape.** A symlink inside `cd` pointing at `$HOME` could expose files outside the
   project. Mitigation: symlinks skipped by default in both tools (already in §3.4).
3. **Guard false negatives.** Files created by `bash` (e.g. `git checkout`, `cargo build`) are not in
   the read-set, so the first model write to them is treated as "existing but unread" → refused. This
   is the *safe* direction but may surprise; the refusal message tells the model exactly what to do.
4. **Guard bypass via `bash`.** `bash` can overwrite files wholesale and is intentionally exempt. The
   guard is not a sandbox (§8.4) — do not document it as one.
5. **MCP output volume.** A `tools/call` returning megabytes of JSON can blow the context window
   despite the byte cap (256 KiB ≈ tens of thousands of tokens). Truncation must be **visible** to the
   model (a `"(truncated)"` marker), never silent.
6. **MCP side effects bypass the guard.** An MCP "filesystem" server could write where the Tool Guard
   cannot see it. Documented limitation; mitigable only by per-profile allowlists (§5.7).
7. **Unbounded MCP servers.** A server that never responds on `initialize` is dropped after the
   handshake timeout; one that dies mid-session is restarted by the supervisor with a full
   re-handshake. Watch for restart storms: `MCP.Server` exits `:normal` on clean detach so
   `:transient` does not restart it.
8. **MCP server sharing across sessions.** Two sessions in the same `cd` share one `MCP.Server`; a
   hung server stalls both. Ref-counting keeps this *visible* (`MCP.servers/1` lists owners) even
   though it is not avoided.
9. **`Tools.schemas/1` is called on every LLM turn** (`start_llm_turn/1`). `MCP.tools_for/1` must be
   a cache read (never a synchronous `tools/list`), or every turn pays a network round-trip.
10. **Tool-name collisions after sanitisation.** `a.b` and `a-b` both become `a_b`. The reverse map
    must detect a clash at discovery time and suffix `_2`, `_3`, … deterministically.
11. **Interaction with §7.2/§7.5.** A verifier (`:shell` mode) may want `glob`/`grep` for evidence
    gathering; nothing here blocks that. Guard read-sets are per session, so a GoalManager-driven
    worker keeps its own.
12. **Daemon ownership.** MCP ports live in the daemon BEAM node; a TUI attach/detach must not touch
    them (`Agent.terminate/2` only fires when a *session* dies).
13. **Existing test churn.** **G6**: the schema-name assertion *will* fail when `glob`/`grep` land.
    This is intentional; the PR must update it in the same commit or CI goes red.

### Open questions (require a user/Conductor decision before coding)
- **OQ-S1 — `.gitignore` matcher.** Hand-roll a minimal matcher (no new dep, correct for common
  patterns) or add a dependency (e.g. a `gitignore`-parsing hex package)? Recommendation: hand-roll
  the documented subset, and *log* (once per search root) that only a subset is honoured.
- **OQ-S2 — `grep` engine.** Pure `:re` per line (simple, no binary dependency) vs. shelling to
  `rg`/`grep` (faster on huge trees, weaker guarantees, contradicts C1). Recommendation: pure Elixir.
- **OQ-S3 — Should `glob`/`grep` be available to `:worker` sessions or `:conductor` only?**
  Recommendation: **all sessions** (they replace `bash find`/`grep`, which workers already have).
- **OQ-S4 — Guard scope.** Does a `read_file` in an earlier *turn* authorise a write in a later turn
  for the same session? Recommendation: **yes** (session-scoped, not turn-scoped) — re-reading on
  every turn is pointless token cost.
- **OQ-S5 — Guard on `write_file` to a path created earlier *in the same session* by
  `write_file`.** Recommendation: allowed (the session authored it; it is in the read-set after the
  write).
- **OQ-M1 — server sharing granularity.** Per-session server process vs. shared-per-`cd`+profile
  (proposed). Shared is cheaper (one Postgres connection pool) but couples blast radius.
- **OQ-M2 — `mcp_command_allowlist/0` default.** Explicit allowlist (`npx`, `uvx`, `node`, `python3`,
  `docker`) vs. `:any` with a warning. Recommendation: allowlist, with `:any` as an explicit
  opt-out.
- **OQ-M3 — hand-roll JSON-RPC/transports or depend on an MCP library?** No MCP dep exists in
  `mix.exs`; `AGENTS.md` prefers lightweight pure-Elixir deps. Recommendation: hand-roll (the
  protocol surface used here is small: 4 methods + 2 notifications).
- **OQ-M4 — SSE in scope for v1?** It is more code (endpoint event, POST correlation, reconnect) than
  stdio. Recommendation: ship **stdio first** (M3), SSE second (M4); the `Transport` behaviour makes
  this a clean split.
- **OQ-M5 — server→client `sampling/createMessage`.** Answer `-32601` (proposed) or route it to the
  session's own LLM (`llm_fn`)? The latter is powerful (server-driven inference) and a lot of trust.
- **OQ-M6 — tool-name prefix.** `mcp__<server>__<tool>` (proposed) vs. `mcp_<server>_<tool>`; the
  double underscore is chosen to be visually unambiguous, but 64-char truncation is likelier with
  long server keys.
- **OQ-M7 — Should MCP tools be gated behind the Tool Guard or a confirmation prompt?** A
  consequential server (Postgres, GitHub) arguably deserves a human-in-the-loop first call.
  Recommendation: out of scope for v1; note it for §7.3 watchers.

## 13. Definition of done

- `glob` and `grep` are available to all sessions, are ignore-aware and capped, and never invoke a
  shell (`grep -rn "shelling out"`-free by construction: no `System.cmd` in the new modules).
- A session cannot overwrite an existing file it has not read, and the refusal is a clear, actionable
  tool result — verified by a test that asserts the on-disk file is unchanged.
- An MCP stdio server declared in `~/.athanor/mcp.json` can be attached to a Conductor or Sub-Agent by
  profile; its tools appear namespaced in `Tools.schemas/1` and are callable via `Tools.execute/3`;
  killing the server degrades gracefully.
- Project-local MCP config is inert unless explicitly enabled; commands are allowlisted, env-scrubbed,
  shell-free, and logged.
- `mix format --check-formatted`, `mix compile --warnings-as-errors`, `mix test` all green.
